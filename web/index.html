01 /

资料很多，为什么这样决定却很难找回。

起点来自整理项目经验的真实需求：结论散在聊天里，方案分布在多个版本中，资深同事的建议离开情境后，很容易被错误概括。

A

文件问答缺少过程

只找到一句话，仍不知道它针对什么问题、有没有被采纳。

B

总结容易越过证据

“建议验证”变成“已经完成”，转述变成本人观点。

C

经验不容易复用

缺少原始背景和适用条件，无法判断方法何时成立。

02 /

我做的关键选择：先保住证据，再形成知识。

产品判断如何落到设计为什么这样取舍
完整聊天优先先浏览上下文，再选择消息建立讨论避免摘句丢失条件与否定关系
同一证据，双线整理项目变化与人物情境观点共享来源既还原事情，也积累判断方式
AI 输出只进入草稿核对引用、身份、表达类型和执行状态后确认程序验证引用存在，人工判断含义是否成立
修订不能抹掉历史消息校订分版本；受影响卡片重新待复核保留可解释性，承担额外版本管理成本
演示与私人数据分离独立部署、独立本机数据库、重新编写案例无需展示内部材料，也能展示产品价值
03 /

不看空白工作台，直接体验一次判断。

为什么没有给所有回答增加追问？

从虚构的「星帆助手」评审出发，选择证据、核对错误状态，再回到原消息。最后修改来源，观察已确认结论如何进入待复核。

开始引导演示 →自由探索工作台 ↗
示例草稿由程序预先编写，演示不会调用模型。核对、引用验证、校订与保存使用实际产品逻辑。

01 / 状态不能跳步

把建议标为“已完成”，确认会被证据规则阻止。

02 / 观点必须有情境

展示“此人在本次评审中的判断”，不推断完整人格。

03 / 来源可以修订

校订正文直接更新显示，旧版本仍可解释历史引用。

04 /

可体验的实现，与尚未跨过的边界。

公开版，可直接体验私人版能力，本演示不连接后续计划
聊天与文件导入、原件预览、逐消息附件、校订历史用户隔离的云同步与历史备份更准确的 OCR 消息分段
讨论、项目、人物、证据卡与人工确认实际模型生成草稿更完整的删除和索引失效策略
本机全文检索、结构化过滤与上下文只读 MCP 已在私人会话实测语义检索与受控草稿回写

公开版不提供在线模型、跨设备同步或私人 MCP。OCR 在浏览器执行，首次需下载第三方引擎和语言包。未提取的文件内容不能被全文检索。

05 /

用可验证的质量，替代漂亮但空泛的结果。

出处是否准确

逐字引用能否定位到对应消息版本？校订后是否提示复核？

判断是否越界

建议是否被误报为完成？人物归属和观点适用范围是否有依据？

是否能够交付

演示可操作、源码可运行、备份可恢复、测试可复现。

当前证据边界

已建立功能和规则测试；未开展正式用户研究或量化效果实验。这里不声称用户规模、节省时间、召回率或业务提升百分比。

06 /

我的贡献，以及从中带走的方法。

胡嘉育 / AI 产品方向

负责问题定义、信息结构、交互流程、证据规则与验收标准；借助 AI 完成代码开发与迭代。通过真实使用中的问题持续调整产品。

这次实践让我将“用户问题—产品取舍—实现—验证”串成闭环，也更清楚模型能力与产品责任的边界。

可复用的产品方法

先定义什么不能被误判，再设计状态与证据；先验证完整用户路径，再评价单个输出；先保留可回退的数据，再做自动整理。
